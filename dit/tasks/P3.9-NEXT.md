## Objective

Meningkatkan alert dari notifikasi in-app menjadi workflow operasional yang dapat di-acknowledge, dieskalasi, dikirim ke endpoint eksternal secara andal, dan menjalankan recovery terbatas dengan audit serta guardrails.

## Non-goals

- Tidak mengirim email/SMS/push kecuali provider dan scope disetujui terpisah.
- Tidak melakukan auto-retry upload yang hasilnya ambigu.
- Tidak mengubah strategi upload/resumable protocol tanpa task khusus.
- Tidak men-deploy atau mengubah production environment.
- Tidak menambah dependency/provider sebelum analisis biaya, security, dan persetujuan.

## Workstream

### P3.9.1 — Execution reconciliation
- Definisikan threshold untuk run berstatus `running` terlalu lama.
- Tandai interrupted run dengan status terminal yang eksplisit atau status khusus yang konsisten.
- Pastikan reconciliation idempotent dan tidak mengubah run yang masih aktif.
- Tambahkan test untuk process crash, overlapping scheduler, dan clock boundary.

### P3.9.2 — Alert lifecycle and escalation
- Alert acknowledgement, acknowledgedBy, acknowledgedAt, dan optional snooze/escalation policy.
- Definisikan severity, escalation window, dan resolve/reopen behavior.
- Hindari notification spam dan race pada alert activation.
- Audit setiap perubahan lifecycle.

### P3.9.3 — External webhook delivery
- Konfigurasi endpoint per owner/tenant sesuai authorization model.
- Sign payload dengan secret yang disimpan aman; jangan expose secret ke client/log.
- Delivery ledger: pending, delivered, retrying, failed, dead-letter.
- Timeout, bounded exponential backoff, idempotency key, payload versioning, dan replay protection.
- SSRF protections: batasi skema/host/IP private/loopback/link-local, validasi DNS dan redirect policy.
- Per-user isolation, endpoint verification, secret rotation, dan redacted logs.

### P3.9.4 — Guarded recovery automation
- Mulai dari rekomendasi/dry-run, bukan auto-mutation.
- Setiap aksi recovery harus memiliki allowlist, precondition, idempotency, audit log, dan kill switch.
- Upload retry hanya boleh setelah YouTube session/state reconciliation.
- Tidak boleh otomatis menghapus upload session atau membuat publikasi duplikat.
- Minta approval operator untuk aksi berisiko tinggi.

### P3.9.5 — Validation and runbooks
- Unit/integration tests untuk retries, duplicate events, race conditions, provider outage, SSRF, secret rotation, dan authorization.
- Staging end-to-end test dengan webhook receiver terkontrol.
- Runbook incident, replay, endpoint disable, secret rotation, dan rollback.
- Update dashboard untuk delivery status dan escalation history.

## Acceptance criteria

- [ ] Stale `running` worker runs terdeteksi dan direkonsiliasi tanpa mengganggu worker aktif.
- [ ] Alert lifecycle dapat di-acknowledge dan escalation behavior deterministik.
- [ ] Webhook delivery idempotent, signed, retry-bounded, auditable, dan tenant-scoped.
- [ ] SSRF protections dan endpoint validation diuji.
- [ ] Recovery automation default dry-run dan memiliki kill switch.
- [ ] Tidak ada retry upload ambigu yang dapat menghasilkan duplikasi tanpa reconciliation.
- [ ] Semua API baru memiliki Zod validation, authz, ownership scoping, dan tests.
- [ ] Prisma schema/indexes dan migration/deployment plan ditinjau.
- [ ] CI seluruhnya lulus; staging evidence dicatat terpisah.
- [ ] Docs, workflow, dan project state diperbarui.
